# Testing — Vitest

> **이 문서를 읽는 사람**: 개발을 이제 막 시작한 사람을 위한 문서다. "테스트가 뭔지", "왜 필요한지", "Vitest라는 도구는 어떤 성격인지"를 다룬다.

---

## 먼저, 한 문장 요약

> **Vitest(바이테스트)**는 우리가 만든 함수/컴포넌트가 "의도한 대로 동작하는지" 자동으로 확인해주는 도구다.

수학 문제 답을 검산하는 것과 비슷하다. 풀어본 다음에 답이 맞는지 자동으로 검사해주는 셈이다.

---

## 왜 필요한가요?

코드를 작성하면 두 가지 일이 벌어진다:

1. **지금 이 순간 동작하는가?** — 직접 브라우저에서 띄워본다
2. **나중에 코드를 고쳐도 여전히 동작하는가?** — 이게 테스트다

2번이 왜 중요하냐면, **우리가 작성한 코드를 나중에 누군가(혹은 미래의 나)가 고칠 수 있기 때문이다.**

예를 들어:

```ts
// 가격을 "12,000원"으로 표시하는 함수
function formatPrice(n: number) {
  return `${n}원`
}

// 어떤 사람이 "쉼표를 넣자"고 고친다
function formatPrice(n: number) {
  return `${n.toLocaleString()}원`  // → "12,000원"이 된다, 좋아!
}

// 그런데 누군가 실수로 이렇게 고친다면?
function formatPrice(n: number) {
  return `${n}원`  // 다시 쉼표가 사라짐 ㅠㅠ
}
```

**테스트가 있으면** 두 번째 수정에서 자동으로 "어? 12000원이 '12,000원'으로 안 나오잖아!" 라고 알려준다.

---

## 다른 도구들과 비교

테스트 도구도 많다. 그런데 왜 Vitest를 쓸까? 대표적인 대안들과 비교해보자.

| 이름 | 뭔가요 | 왜 안 골랐나요 |
|------|--------|----------------|
| **Jest(제스트)** | 가장 오래된, 가장 유명한 테스트 도구 | 설정이 까다롭고, TypeScript/ESM과 함께 쓰려면 추가 설정이 많음 |
| **Vitest** ✅ | Jest와 **사용법이 거의 같은데**, 더 빠르고 설정이 단순 | — |
| **Playwright / Cypress** | 브라우저에서 클릭하고 스크린샷 찍는 테스트 | **E2E 테스트**용 — 이 문서의 범위보다 큰 주제 |
| **React Testing Library** | 테스트 도구가 아니라 **DOM 찾는 도우미** | Vitest/Jest 어느 쪽이든 같이 쓰이는 동반자 |

핵심 메시지:

> "Jest라는 이름을 많이 들어봤을 거다. **Vitest는 Jest를 더 빠르고 쉽게 만든 버전**이라고 생각하면 된다. 사용법이 거의 같으니까 나중에 Jest를 만나도 당황하지 않는다."

---

## 핵심 개념 — 테스트 피라미드

모든 테스트가 같은 건 아니다. **위에서 아래로 갈수록 더 많고, 더 빠르다.**

```
        ▲
       / \
      / E \      E2E 테스트 (Playwright/Cypress)
     / ---- \    - 실제 브라우저로 클릭·입력
    /  통합   \   - 느림, 비용 큼, 신뢰도 높음
   /-----------\
  /  컴포넌트    \  Vitest + React Testing Library
 /   테스트       \  - 컴포넌트를 그려보고 확인
/------------------\
     단위 테스트     Vitest
     - 함수 하나하나
     - 빠름, 비용 작음
```

이 문서에서는 **가장 아래 두 층**만 다룬다.

> 💡 비유: **회사 검사의 비유** —
> - 단위 테스트 = 각 부품(함수) 검사
> - 컴포넌트 테스트 = 조립된 모듈(상품 카드) 검사
> - E2E 테스트 = 완성된 차를 실제로 도로에서 굴려보는 것

## Vitest의 핵심 특성

### 1. 한 테스트는 한 가지만 검사한다

```ts
// ✅ 좋은 테스트: 한 가지만 검사
it('12000원을 "12,000원"으로 표시한다', () => {
  expect(formatPrice(12000)).toBe('12,000원')
})

// ❌ 나쁜 테스트: 여러 가지를 한꺼번에 검사
it('가격 표시가 잘 된다', () => {
  expect(formatPrice(0)).toBe('0원')
  expect(formatPrice(12000)).toBe('12,000원')
  expect(formatPrice(1000000)).toBe('1,000,000원')
  // 만약 하나가 실패하면, 위 세 개 중 뭐가 문제인지 알기 어렵다
})
```

> 💡 비유: **수학 시험 문제 한 줄 = 한 개념**이다. 한 줄에 여러 개념을 우겨넣으면 채점할 때 어디서 틀렸는지 모른다.

---

### 2. Given–When–Then 패턴

테스트 본문은 사실상 세 부분으로 나뉜다:

```ts
it('12000원을 "12,000원"으로 표시한다', () => {
  // Given: 입력 준비 (이런 값이 들어오면)
  const input = 12000

  // When: 동작 수행 (이 함수를 실행하면)
  const result = formatPrice(input)

  // Then: 결과 확인 (이렇게 나와야 한다)
  expect(result).toBe('12,000원')
})
```

이게 사실상 모든 테스트의 뼈대다. **이 세 단락을 주석으로 나눠 쓰는 것**만으로도 코드 가독성이 크게 좋아진다.

> 💡 비유: **레시피**와 같다.
> - Given = 재료 준비
> - When = 조리
> - Then = 맛 확인

---

### 3. Vitest만의 특별한 점

Jest와 비슷하지만, Vitest만의 차별점이 있다:

| 특징 | 설명 |
|------|------|
| **빠르다** | 내부적으로 Vite/esbuild라는 도구를 써서 코드 변환이 거의 즉시 일어난다 |
| **TypeScript 기본 지원** | 따로 설정 안 해도 TypeScript 코드를 바로 테스트한다 |
| **Jest와 사용법이 거의 같다** | 나중에 Jest를 만나도 적응이 빠르다 |
| **`--ui` 모드** | 브라우저에서 테스트 결과를 그래프로 보여준다 |
| **Watch 모드** | 파일을 저장하면 자동으로 테스트가 다시 돌아간다 |

---

### 4. React Testing Library는 "사용자 관점"을 강제한다

Vitest로 React 컴포넌트를 테스트할 때는 보통 **React Testing Library(RTL)** 라는 걸 같이 쓴다.

RTL의 핵심 철학은 이거다:

> **"구현의 내부 동작이 아니라, 사용자가 실제로 보고/하는 것을 테스트하라."**

예를 들어:

```tsx
// ❌ 구현 디테일에 의존 (테스트가 깨지기 쉬움)
const button = container.querySelector('.btn-primary')

// ✅ 사용자 관점 (의미 기반)
const button = screen.getByRole('button', { name: '장바구니 담기' })
```

전자는 클래스 이름이 바뀌면 테스트가 깨진다. 후자는 "역할"과 "이름"으로 찾기 때문에 **리팩토링(코드 개선)에 강하다.**

> 💡 비유: **외관 검사 vs 시트벨트 검사** —
> - 외관(클래스명)이 바뀌어도 자동차의 본질(시트벨트 역할)은 같다.
> - 우리는 "본질"로 테스트해야 한다.

---

### 5. 자동 재실행 — Watch 모드

테스트를 짜는 흐름은 보통 이렇다:

```
1. 테스트 작성
2. 실행 → 빨간 줄 (실패)
3. 코드 작성
4. 실행 → 초록 줄 (성공)
5. 코드 개선 → 다시 실행 (여전히 초록?)
```

이 흐름을 빠르게 돌게 해주는 게 **Watch 모드**다. 파일을 저장할 때마다 자동으로 테스트가 다시 돈다.

> 💡 비유: **운동할 때 거울을 보는 것**과 같다. 자세를 고칠 때마다 거울로 확인한다.

---

## 학생이 꼭 가져갈 인사이트

1. **테스트는 디버깅 도구다.** 작성 중에 버그를 찾는 가장 빠른 방법이다.
2. **한 테스트 = 한 가지 단언.** 두 가지를 확인하고 싶으면 테스트를 둘로 나눠라.
3. **사용자 관점으로 테스트하라.** 클래스명이 아니라 역할(role)과 이름(name)으로 찾아라.
4. **`--ui` 모드를 써라.** 테스트가 그래프로 보이면 훨씬 직관적이다.
5. **테스트는 점진적으로 늘려라.** 100% 커버리지가 목표가 아니라, **자주 깨지는 곳 / 중요한 곳**에 두는 게 핵심이다.

---

## 절대 하면 안 되는 안티패턴

| ❌ 이렇게 하지 마세요 | ✅ 이렇게 하세요 |
|----------------------|------------------|
| 구현 디테일에 의존 (`getByTestId` 남용) | 의미 기반 쿼리 (`getByRole`, `getByText`) |
| 한 테스트에 단언 5개 | 테스트를 5개로 분리 |
| 테스트끼리 상태 공유 | 각 테스트는 독립적으로 준비/정리 |
| `setTimeout`으로 비동기 대기 | `findBy*` 또는 `waitFor` 사용 |
| 100% 커버리지에 집착 | 핵심 비즈니스 로직에 집중 |

> 💡 **가장 중요한 한 줄**: "테스트는 **코드를 얼마나 검증했느냐**가 아니라, **다음 사람이 코드를 고칠 때 안심할 수 있게 해주느냐**로 평가된다."
