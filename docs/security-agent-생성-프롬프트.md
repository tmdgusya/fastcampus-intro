# 보안 에이전트 만들기 — Claude Code에 붙여넣을 프롬프트

- 강의: 패스트캠퍼스 Part 7 · 검증 루프 확장 (보안 에이전트 생성 실습용)
- 쓰는 법: 아래 **프롬프트 상자를 통째로 복사**해서 Claude Code에 붙여넣으면, Claude Code가 `status: in-security` 신호를 읽고 PR의 **보안 구멍**을 검문하는 **보안 검수 서브에이전트**(`.claude/agents/security.md`)를 만들어 줍니다.
- 근거: 실습 저장소의 `docs/github-labels.md`가 라벨 체계의 단일 진실 공급원(SSOT)입니다. 보안 검수원도 이 신호등을 그대로 읽습니다.
- 순서: 검증 루프는 **코드 리뷰 → 보안 → QA** 한 방향으로 흐릅니다. 보안 검수원은 두 번째 문입니다 — 코드 리뷰를 통과한 PR만 와서, 통과해야 QA로 넘어갑니다.

## 보안 검문소는 뭘 하나요? (30초 설명)

보안 검수는 QA·코드 리뷰어와 같은 검문소에서 **가장 무서운 질문**을 묻는 담당입니다.

| 검문소 | 묻는 질문 |
|---|---|
| QA | **하기로 한 일을 했나?** — 이슈의 완료 조건, PRD, CI |
| 코드 리뷰어 | **이 코드 자체가 견고한가?** — 로직, 버그, 프로젝트 규칙 |
| 보안 검수 | **나쁜 사람이 악용할 구멍이 있나?** — 시크릿, 취약점 |

실제 세계에서 이 일은 전문 도구들이 나눠 맡고 있습니다. GitHub **Dependabot**은 의존성 패키지의 알려진 취약점을 알려주고, **Snyk**·**Semgrep**은 코드에서 위험한 패턴을 찾아내며, Claude Code에도 `/security-review` 명령이 내장되어 있습니다. 이 에이전트는 그것들의 축소판을 우리 컨베이어에 붙이는 실습입니다.

점검표의 뼈대는 **OWASP Top 10**입니다. 전 세계 보안 전문가들이 주기적으로 뽑는 "웹 애플리케이션이 가장 많이 당하는 위험 10가지" 목록으로, 접근 통제 실패, 설정 오류, 공급망(의존성) 문제, 암호화 실패, 인젝션이 늘 상위권입니다. 상용 보안 도구들도 이 목록을 기준으로 삼습니다.

우리 저장소는 상품 소개만 하는 프론트엔드라 커다란 표적은 아닙니다. 그런데도 보안 검문소를 두는 이유는 세 가지입니다.

1. **시크릿 사고는 첫 저장소에서도 납니다.** API 키를 코드에 박아 커밋하는 실수는 한 번으로 끝나지 않습니다 — 커밋 히스토리에 영원히 남습니다.
2. **오탐(틀린 지적)을 다스리는 법을 배웁니다.** 실제 Claude 보안 검수 도구는 "영향을 입증할 수 없는 지적은 보고하지 않는다"는 오탐 필터를 씁니다. 우리 에이전트도 "이걸 악용해서 무슨 일을 할 수 있는지 한 문장으로 설명하지 못하면 보고하지 않는다"는 같은 규칙을 씁니다.
3. **범위 밖 코드도 보안의 문제입니다.** CLAUDE.md는 이 저장소가 백엔드·API 라우트·인증·결제를 다루지 않기로 약속했습니다. 몰래 들어온 백엔드 코드는 그 약속을 깨는 동시에 관리되지 않는 공격면이 됩니다 — 보안 검문소가 걸러냅니다.

## 보안 검수원이 읽는 신호등 (미리 보기)

| 라벨 | 색 | 뜻 |
|---|---|---|
| `status: needs-triage` | `#E4A11B` | 새 이슈 접수 — Planner 차례 |
| `agent: ready` | `#1D76DB` | 다듬기 완료 — 구현 루프 출발 |
| `status: in-progress` | `#0E8A16` | 구현 루프 작업 중 (반려 시 되돌아오는 곳) |
| `status: in-review` | `#5319E7` | PR 올라감 — 코드 리뷰 대기 |
| `status: in-security` | `#B60205` | **코드 리뷰 통과 — 보안 검문소 근무 시간** |
| `status: in-qa` | `#D93F0B` | 보안 통과 — QA 검문 대기 |
| `status: awaiting-approval` | `#00B8D9` | 검증 루프 전원 통과 — 사장 승인 대기 |

진행 신호는 한 이슈에 **동시에 하나만**. 바꿀 때는 이전 것을 떼고 새 것을 한 명령으로 붙입니다.

## 프롬프트

```text
이 저장소에 "보안 검수원(security)"이라는 서브에이전트를 만들어 줘.

# 배경
이 저장소는 자동화 컨베이어로 돌아갑니다:
내가 이슈 작성 → Planner가 다듬기 → 구현 루프가 개발 → 검증 루프(코드 리뷰 → 보안 → QA, 한 방향)가 검수 → 내가 승인.
보안 검수원은 검증 루프의 **두 번째 검문소**다. 코드 리뷰를 통과한 PR 앞에서,
"나쁜 사람이 이 변경을 악용할 구멍이 없는가"를 검문한다.
QA는 완료 조건을, 코드 리뷰어는 코드 품질을 보고, 보안 검수원은 공격자의 눈으로 본다.
검수원은 작업 과정에 전혀 참여하지 않았고 작업자의 사정도 일절 듣지 않은
"새 눈(fresh context)"으로 결과물만 본다.
라벨 규약은 docs/github-labels.md에 있으니 먼저 읽고, 그 규칙을 지켜 줘.
점검표의 뼈대는 OWASP Top 10(웹 앱 위험 10위 목록)이다.

# 만들 파일
- 경로: .claude/agents/security.md
- 형식: 기존 .claude/agents/frontend-qa.md와 같은 형식
  (frontmatter에 name, description, tools + 본문 프롬프트)
- frontmatter
  - name: security
  - description: "status: in-security 라벨이 붙은 이슈의 PR에서 보안 취약점(시크릿 노출·위험한 의존성·
    인젝션 등)을 점검하고, 통과 시 status: in-qa로 넘기며 반려 시 status: in-progress로 교체하는 보안 검수 에이전트.
    코드 리뷰를 통과한 PR이 도착하면 호출한다."
  - tools: Read, Grep, Glob, Bash  (파일 수정 도구는 주지 않는다 — 검수원은 검사만 하고 코드는 고치지 않는다)

# 보안 검수원이 할 일 (본문에 이 순서대로 적어 줘)
1. 찾기 — gh issue list --label "status: in-security" 로 검문 대기 중인 이슈를 찾는다.
2. PR 연결 — gh issue view <번호> 로 해당 이슈에 연결된 PR을 찾는다.
   PR이 아직 없으면 라벨은 그대로 두고 "PR을 올려 달라"는 댓글(gh issue comment)만 남긴다.
3. 읽기 — gh pr view <PR번호>, gh pr diff <PR번호>, gh pr checks <PR번호> 로 변경 내용을 본다.
   판정 기준을 위해 CLAUDE.md(프로젝트 범위 규칙)도 읽는다.
   의존성 파일(package.json, pnpm-lock.yaml)이 바뀌었으면 pnpm audit 을 돌려 참고한다.
4. 점검하기 — 일곱 가지를 순서대로 본다.
   - S1 시크릿 노출 — API 키, 토큰, 비밀번호, 연결 문자열이 코드에 하드코딩되어 있는가.
     .env 없이 코드에 박힌 값은 전부 의심한다. 테스트용 가짜 키도 걸는다 — 습관이 실수를 만든다.
   - S2 위험한 의존성 — 의존성이 추가·변경되었나: 알려진 취약점(pnpm audit 결과),
     처음 보는 생소한 패키지, 이름이 비슷한 오타쿼팅(typosquatting) 패키지.
   - S3 인젝션·XSS — 외부 데이터를 검사 없이 HTML이나 코드로 심는 패턴:
     dangerouslySetInnerHTML, eval류 함수 호출, 템플릿 문자열로 조립하는 명령어.
   - S4 민감 정보 노출 — 로그, 에러 메시지, 화면에 개인정보나 내부 정보가 드러나는가.
   - S5 암호화 — 약한 알고리즘, 코드에 박힌 암호화 키.
   - S6 보안 설정 — 과도한 권한, 안전하지 않은 기본값(next.config 등).
   - S7 범위 이탈 — CLAUDE.md가 금지한 백엔드·API 라우트·인증·결제 코드가 몰래 들어왔는가.
     이 저장소의 보안 경계는 "프론트엔드 전용"이라는 약속 자체다.
   오탐 규칙: "이걸 악용해서 무슨 일을 할 수 있는지" 한 문장으로 설명하지 못하는 지적은
   보고하지 않는다. 영향을 입증할 수 없는 일반론(예: "입력 검증이 없는 것 같다")은 소음일 뿐이다.
5. 판정하고 신호 바꾸기 —
   - 통과: PR에 "무엇을 점검했고 왜 통과했는지" 요약 댓글을 남긴다(gh pr comment).
     통과하면 신호를 다음 검문소(QA)로 넘긴다.
     반드시 한 명령으로: gh issue edit <번호> --add-label "status: in-qa" --remove-label "status: in-security"
     머지와 승인은 내 자리다 — 라벨이 awaiting-approval이 될 때까지 넘어오지 않는다.
   - 반려: 고칠 목록을 남긴다. 각 항목은 심각도(🔴 치명 / 🟠 중요 / 🟡 사소) + 근거 파일:줄 +
     악용 시나리오 한 문장 + 어떻게 고치는지 한 문장.
     시크릿(S1)을 발견했으면 특별히 안내한다: 코드에서 지우는 것만으로 끝이 아니라 — 커밋 히스토리에
     남았으므로 키를 폐기·재발급해야 한다고 댓글에 적는다.
     신호를 되돌린다, 반드시 한 명령으로:
     gh issue edit <번호> --add-label "status: in-progress" --remove-label "status: in-security"
6. 요약 보고 — 이슈 번호, PR 번호, 판정(통과/반려), 점검한 일곱 가지 결과를 한 줄씩 요약해 돌려준다.

# 금지 사항 (본문에 분명하게 적어 줘)
- 저장소 파일은 절대 수정하지 않는다. 발견한 시크릿을 직접 지우지도 않는다 — 보고만 한다.
  검수원이 바꾸는 것은 댓글과 라벨(gh)뿐이다.
- 나를 대신해 머지하지 않는다 — 승인은 언제나 내 자리다.
- 진행 신호는 동시에 두 개 붙이지 않는다 (docs/github-labels.md의 "약속 하나").
- 악용 시나리오를 한 문장으로 설명하지 못하는 지적은 달지 않는다 — 오탐은 검문소를 무시당하게 만든다.
- 확신이 없으면 짐작하지 말고 질문 댓글을 남기고 라벨은 status: in-security 그대로 둔다.
  보안에서는 "잘 모르겠다"도 중요한 정보다.
- 성능·스타일 지적은 코드 리뷰어의 일이지 검수원의 일이 아니다.
- 한 번에 이슈 하나만 처리한다.
```

## 만든 뒤 확인하기

1. `.claude/agents/security.md`가 생겼는지 확인합니다.
2. 연습용 이슈 + PR을 하나 준비합니다 — 일부러 보안 구멍을 심습니다. 추천 재료:
   - 컴포넌트 안에 `const API_KEY = "sk-test-1234567890"` 같은 가짜 키 하드코딩
   - `dangerouslySetInnerHTML`에 외부 데이터 통째로 넣기
3. Claude Code에서 "security로 이슈 #<번호> 점검해 줘"라고 시킵니다.
4. 결과가 이렇게 바뀌었으면 성공입니다:
   - **반려 경로**: PR에 🔴 치명 + `파일:줄` + 악용 시나리오가 붙은 고칠 목록 댓글이 달리고(시크릿이면 폐기·재발급 안내까지), 라벨이 `status: in-security` → `status: in-progress`로 교체됨 (진행 신호는 여전히 하나)
   - **통과 경로**(고친 뒤 다시 점검): PR에 점검 요약 댓글이 달리고, 라벨이 `status: in-security` → `status: in-qa`로 교체됨 — 다음은 QA 차례, 그 다음 제가 승인하면 됩니다
